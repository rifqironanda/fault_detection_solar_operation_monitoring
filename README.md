# Fault Detection Solar Operation Monitoring

A modular research prototype for photovoltaic (PV) operational monitoring and anomaly-based fault indication.

The application is designed around a practical monitoring workflow:

`Raw measurements → validation → physics-informed baseline → per-inverter anomaly detection → explainable alerts → dashboard`

It is intended to help distinguish output reductions that can be explained by environmental conditions from operating conditions that are statistically unusual and may require further inspection.

## Capabilities

- CSV upload for new PV monitoring datasets.
- Data-schema validation and upload preview.
- Inverter-level filtering and fleet-level status overview.
- Physics-informed expected-power estimation using irradiance and temperature.
- Performance Ratio (PR) calculation.
- Isolation Forest anomaly detection trained independently for each inverter.
- Rule-based, explainable alerts.
- Actual-versus-expected power and PR visualizations.
- Unit tests for alert-generation logic.

## Data contract

The dashboard accepts a CSV containing these required fields:

| Field | Unit | Description |
|---|---|---|
| `timestamp` | datetime | Measurement timestamp; timezone should be documented |
| `inverter_id` | — | Inverter identifier |
| `irradiance_w_m2` | W/m² | Solar irradiance |
| `ambient_temp_c` | °C | Ambient temperature |
| `power_kw` | kW | Measured PV output |
| `voltage_v` | V | Measured voltage |
| `current_a` | A | Measured current |

Derived fields are generated by the pipeline and do not need to be uploaded:

`expected_power_kw`, `performance_ratio`, `electrical_power_estimate_kw`, `power_consistency_ratio`, `is_anomaly`, `anomaly_score`, and alert fields.

See [DATA_CONTRACT.md](DATA_CONTRACT.md) for the current contract and recommended future fields.

## Using your own data

Run the application:

```powershell
streamlit run app.py
```

In the sidebar, select **Upload CSV**, choose a file, and inspect the validation summary. The interface reports detected columns, number of records, number of inverters, invalid timestamps, missing values, duplicate `timestamp + inverter_id` keys, and the available time range.

A dataset is not treated as ready for monitoring unless the required schema and basic data-quality checks pass.

The repository also contains a sample dataset under `data/raw/pv_monitoring_dataset.csv`.

## Method

### Physics-informed baseline

The prototype estimates expected output as:

```text
P_expected =
    P_rated
    × (G / G_reference)
    × [1 + γ × (T_ambient - T_reference)]
```

The current implementation uses ambient temperature as a proxy for cell temperature. This is a prototype assumption and should be replaced or calibrated using plant-specific engineering data.

Performance Ratio is represented as:

```text
PR = P_actual / P_expected
```

PR is treated as undefined below the configured minimum irradiance threshold to avoid interpreting low-light operation as normal full-load performance.

### Per-inverter anomaly detection

Isolation Forest is applied independently for each `inverter_id`. This addresses the question:

> Is the operating condition of this inverter unusual relative to its own historical operating pattern?

The model uses environmental, electrical, physics-derived, and consistency features. It is an unsupervised detector; an anomaly score represents statistical unusualness, not failure probability or a component-level diagnosis.

### Alert logic

The alert layer combines evidence:

- **INFO**: low irradiance; low output can be environmentally driven.
- **WARNING**: potential underperformance or statistical/electrical inconsistency.
- **CRITICAL**: underperformance combined with an ML anomaly.

Alert messages are intended to support inspection and prioritization rather than automatically declare equipment failure.

## Evaluation for real deployment research

For real plant data, use time-based train/validation/test periods and evaluate:

- precision
- recall
- F1
- false alerts per day
- detection latency
- missed anomalies

Operational validation should additionally consider inverter ratings, sensor quality, curtailment, maintenance windows, availability, weather conditions, and confirmed fault/maintenance records.

## Limitations

This repository is a research and portfolio prototype, not an operational control system.

The current model does not establish root cause. Results depend on the quality and representativeness of the measurement data, selected physical assumptions, alert thresholds, and anomaly-detector parameters. Inverter-specific ratings and plant-specific operating constraints should be introduced before applying the method to an actual PV plant.
